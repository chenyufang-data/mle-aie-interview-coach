## 0. Why this experiment

The README's line "deliberately not embedding-based — measured at 100%
Recall@5 / 0.91 MRR on 23 curated cases" is a strength *because* it was
measured. It has two weaknesses an interviewer can find in a minute:

1. The eval set is saturated. BM25 sits at 23/23, so that set cannot show
   dense retrieval winning — it can only show it tying or losing. A
   comparison at ceiling proves nothing either way.
2. There is one retrieval task in the product where vocabulary mismatch
   actually bites, and it was never measured: the mock interview's
   rubric grounding. `coach/mock/planning.py:attach_rubric_chunks` queries
   `topic + question_hint` — text an LLM wrote from a job description —
   against bank questions written by a course author, and attaches a
   rubric only when raw BM25 ≥ 10 (`RUBRIC_MIN_SCORE`). Every probe that
   scores below that grades against an on-the-fly rubric instead of a
   curated one. Nobody knows what share that is.

So the experiment asks two real questions and answers a third for free:

- **Q1** Does dense or hybrid retrieval beat BM25 where the query's
  vocabulary differs from the bank's? (practice-question retrieval)
- **Q2** Does dense retrieval raise rubric-grounding coverage in the mock
  without lowering the precision of what it attaches? (product-relevant)
- **Q3** At 339 chunks, what does a vector database cost over a numpy
  array? (honesty about the "vector database" line: the store is a
  workflow, not a scale requirement — measure its overhead and say so)

Non-goals: swapping retrieval because embeddings are fashionable; adding
a runtime dependency without a rule that says it earned it; tuning
anything on the evaluation sets.

## 1. Arms

All arms rank the **same document text** (`retrieval.retrieval_text`:
module + topic + tags + question + key points) and apply the **same
filters** (level → difficulty set, module, exclude ids), so the only
variable is the scoring function. Fairness rule: no arm gets extra
fields.

| Arm | What | Runtime deps |
| --- | --- | --- |
| `bm25` | the incumbent `retrieval.Retriever` | none |
| `dense` | `BAAI/bge-small-en-v1.5` (384-d, ONNX via `fastembed`, no torch), cosine over a numpy matrix | fastembed (+ onnxruntime, already installed) |
| `chroma` | the same embeddings in a persistent Chroma collection (cosine space, filters as `where`) — Q3's arm | chromadb |
| `hybrid` | reciprocal-rank fusion (k = 60) of `bm25` and `dense` rank lists, ties broken by chunk id | as `dense` |
| `dense-ml` (stretch, §3 slice D only) | a multilingual model (`paraphrase-multilingual-MiniLM-L12-v2` or `bge-m3`, whichever fastembed lists at install time) | fastembed |

Embedding model choice is fixed before running: bge-small is the strongest
small English model fastembed ships as ONNX; it is *not* to be swapped
after seeing results (that would be tuning on the test set). If bge-small
is unavailable on this machine, fall back to Chroma's default MiniLM-L6
and record the substitution.

**What `BAAI/bge-small-en-v1.5` requires and produces** (verify the size
and version fastembed lists at install time; anything that differs gets
recorded in the results file):

| Property | Value | Why it matters here |
| --- | --- | --- |
| Size | ~33M parameters; ONNX file ≈ 130 MB (fp32) | under R1's 200 MB cap; one download, cached in `data/models/fastembed/` |
| Output | 384-d vector, normalized → cosine = dot product | 339 × 384 floats ≈ 0.5 MB — the whole index fits in a numpy array |
| Context | 512 tokens max | `retrieval_text` is ~50–150 tokens; nothing is truncated |
| Language | English only | fine for banks and set B; slice D needs the multilingual arm |
| Hardware | CPU via onnxruntime (already installed, 1.29); no GPU, no torch | one query ≈ 5–20 ms on CPU, the 339-chunk build takes seconds |
| Extra deps | fastembed → huggingface_hub (download), tokenizers (installed), tqdm, loguru | modest; still experiment-only, never in `requirements.txt` |
| Network | once, to download the model; offline after | pin the cache dir so a clean clone rebuilds deterministically |
| License | MIT | no restriction on shipping if a rule passes |
| Query prefix | v1.5 works without an instruction; the model card still recommends `Represent this sentence for searching relevant passages: ` for short queries → passages | **decided now:** prefix queries, not documents, in every arm that uses the model — not to be toggled after seeing results |

The experiment's dependencies live in `requirements-retrieval-eval.txt`,
never in `requirements.txt`. Runtime stays BM25 unless §2 says otherwise.

## 2. Pre-registered decision rules

The rules refer to four evaluation sets, defined in full in §3:

- **Set A** — the 23 curated queries already in `tests/retrieval_cases.json`
  (BM25 scores 23/23 on them: the ceiling / no-regression check).
- **Set B** — ~69 paraphrases of those 23, written the way a candidate
  would phrase them and filtered so they share no tag vocabulary with the
  target (the vocabulary-mismatch set — the real signal for Q1).
- **Set C** — ~30 mock-interview probe targets with hand-labeled rubric
  fairness (the grounding set — Q2).
- **Set D** — stretch: Chinese originals from the Real Qs bank (cross-lingual).

Measured on CPU, warm (first query excluded), 5 repeats per query, p50/p95
reported. The results file records the hardware (this machine: Ryzen 7
9800X3D, 8c/16t, AVX-512 — far above what a public-repo user may have, so
latency is always reported *with* the CPU model, never bare). GPU is
deliberately unused: CPU ONNX is deterministic and reproducible on any
clone, and at 339 chunks a GPU would change nothing measurable. Counts
are reported next to every percentage — with n = 23 a single query is
4.3 points.

**R1 — practice-question retrieval (Q1).** `hybrid` or `dense` replaces
`bm25` in `coach/kb.py` only if ALL hold:

1. Recall@5 on set A stays 23/23 and MRR on A drops by no more than 0.05
   (no regression on the curated set);
2. Recall@5 on set B improves by ≥ 10 points absolute over `bm25`;
3. warm query latency p95 ≤ 50 ms;
4. the index rebuilds deterministically from committed code (no hand
   steps) and the model download is under 200 MB. Resident-memory growth
   after `load_or_build` (RSS before vs after) is measured and reported,
   not gated: the deployment instance is a free variable (the t3.micro is
   closed; a larger one can be opened), so RAM on the server is a sizing
   decision, not a rule.

*Why a size cap on a shipping rule:* R1 changes what every **public
clone** runs on whatever laptop it is cloned to — that footprint does not
scale with the EC2 instance. The runtime today is `anthropic +
scikit-learn` with a 6.8 MB grader as its largest artifact; the voice
stack is optional precisely because it is heavy. bge-small (~130 MB) is a
tolerable first-start download for a clear retrieval win; a base-size
model (~440 MB) or bge-m3 (~2 GB) is not, whatever it scores. The cap is
set just above the chosen model and well below the next size class on
purpose: a win that needs a bigger model earns a line in the report, not
a runtime change — and writing it down tonight removes tomorrow's
temptation to escalate model size until something wins. If a larger
model is ever to be a contender, that is a change to the arms in §1
(tonight, or as a recorded second experiment), never a quiet raise of
this cap. The cap binds R1 only; the stretch multilingual arm may be any
size because it cannot ship.

Otherwise BM25 stays, and the README gains a measured comparison instead
of an assertion.

**R2 — rubric grounding (Q2).** `attach_rubric_chunks` switches to dense
(or hybrid) scoring only if BOTH hold on set C:

1. grounding coverage (probes that receive a bank rubric) rises by ≥ 15
   points absolute;
2. hand-labeled precision of attached rubrics is ≥ BM25's precision on the
   same probes (no regression in what gets attached).

The dense acceptance threshold is calibrated on sets A + B only (§3), never
on C. C is looked at exactly once, after the threshold is frozen.

**R3 — the store (Q3).** No shipping rule; report Chroma's p95 overhead vs
the numpy arm, index build time, on-disk size, and install weight. The
write-up states plainly whether a vector database earned its place at this
corpus size. Predicted answer: no — and that prediction is written here so
the report can be checked against it.

## 3. Evaluation sets

| Set | Queries | Gold labels | Purpose |
| --- | --- | --- | --- |
| **A** curated | the existing 23 in `tests/retrieval_cases.json` | expected tags / module (existing) | ceiling / no-regression check |
| **B** paraphrase | ~3 rephrasings per A case, ~69 | inherited from the parent case | vocabulary mismatch — the real Q1 signal |
| **C** grounding probes | ~30 probe targets from real plans over the 3 default JDs × 2 levels | hand-labeled "is this rubric fair for this probe?" | Q2 |
| **D** cross-lingual (stretch) | `metadata.original` of rag_exp chunks whose `language` is zh | the chunk itself (id match) | a capability BM25 lacks by construction (tokenizer is `[a-z0-9]+`) — reported as such, not as a "win". *2026-09-04: not run — the bank holds only 2 Chinese originals (52 en, 3 mixed), too few to be a slice.* |

**Building B** (`grader/paraphrase_queries.py`, same conventions as
`label_teacher.py`: free dry run, nothing sent without `--confirm`, cost
printed first):

- One Claude call with all 23 cases: "rephrase each as a candidate would
  type it into an interview-prep chat, three ways, without using the
  technical term the question is about". Estimated cost ≈ $0.10 —
  **needs authorization tomorrow before the call**.
- Automatic mismatch filter: drop any paraphrase whose tokens intersect the
  parent case's `expected_tags` tokens (tags split on `-`), so the set is
  guaranteed to test vocabulary mismatch rather than restate the query.
  *Declared 2026-09-04 before generation, in `grader/paraphrase_queries.py`:*
  the five field-naming tokens {data, model, models, machine, learning} are
  exempt (they name the field, not the target concept); the one tag-less
  case uses its `expected_module` tokens instead; exact duplicates of the
  parent are dropped.
- Hand review (≈ 15 min): delete paraphrases that changed the meaning. The
  survivors are committed as `tests/retrieval_cases_paraphrase.json` with a
  `parent` field pointing at the A query. No personal data involved.

**Building C** (`grader/grounding_eval.py`):

- `--generate --confirm`: run the real planner path (`planning.py`) with
  DeepSeek Flash over `templates.py`'s default JDs × {Mid-level, Senior}
  using `example_resume.txt` as the resume. ~6 plans, ~30 probe targets,
  cost in cents. Probes are saved with their `topic` + `question_hint`.
- `--pool`: for each probe, collect each arm's top-1 candidate (BM25 above
  10; dense above the frozen threshold), union them, and write a labeling
  sheet: one row per (probe, candidate chunk) with the probe text and the
  chunk's question + key points. ≤ 90 rows.
- Hand label each row yes/no ("would this chunk's key points be a fair
  rubric for this probe?"), ≈ 30–40 min. Labels commit as
  `grader/grounding_labels.jsonl` (synthetic probes over public bank
  questions — nothing private).
- **Per probe, one extra label:** `covered` (some bank chunk would be a
  fair rubric, whether or not any arm retrieved it — check the pooled
  candidates plus a quick BM25/dense top-5 skim) or `uncovered` (no bank
  has this topic). This decomposes the coverage gap into *retrieval
  misses* (fixable by a better retriever — Q2) and *content gaps* (fixable
  only by new chunks — §9). The split is the number §9's decision rests on.
- `--score`: coverage and precision per arm, plus the covered/uncovered
  split of the ungrounded probes.

**Dense threshold calibration (before C is opened):** on A + B, compute
BM25-with-threshold-10's top-1 precision ("top-1 is relevant" among queries
where it attaches at all). Choose the cosine threshold at which dense's
top-1 precision on the same queries matches it. Freeze it, write it in the
report, then run C.

## 6. Risks and mitigations

- **chromadb install on Python 3.13 / Windows.** The experiment does not
  depend on it: `dense` (numpy) answers Q1 and Q2 alone; `chroma` only
  answers Q3. If the install fights back for more than 15 minutes, record
  the failure as the Q3 finding and move on.
- **Model download / cache location.** Pin fastembed's cache to
  `data/models/fastembed/` (gitignored). Record model id, size, and hash
  in the results file.
- **Telemetry.** Chroma phones home by default; set
  `ANONYMIZED_TELEMETRY=False` in code before import, not just in the shell.
- **n = 23 is small.** Report counts beside percentages; B (~69) is the
  real Q1 signal; never claim significance the set cannot carry.
- **Paraphrase leakage.** The tag-token filter guarantees mismatch; the
  hand review guarantees meaning. Both are recorded in the report.
- **Tuning on the test set.** The only tunable (dense threshold) is
  calibrated on A + B and frozen before C. Arms and models are fixed in §1
  before the first run. If something *must* change after seeing results,
  it is written down as a post-hoc change, not folded in.
- **Non-determinism.** CPU ONNX embeddings are deterministic; RRF ties
  break by chunk id; Chroma's HNSW is approximate — at 339 vectors set the
  collection to exact search if the API allows, else report recall against
  the numpy arm as a Q3 line.
- **Time.** C is the first thing to drop, and it drops to "pending", never
  to a shortcut (no LLM-judge in place of hand labels on the first pass).

## 9. Conditional follow-up — promoting uncovered probe topics to reviewed chunks

*Raised 2026-09-03: the mock's ungrounded probes are graded against
"expected specifics" the planner LLM invented at plan time
(`coach/mock/report.py` builds the distilled verdict block only for probes
with a `chunk_id`). Should recurring uncovered topics become chunks?*

**Not before the experiment.** Adding chunks moves the ground under sets
A/B mid-comparison, and no retriever can fix a content gap — so first
measure how much of the gap *is* a content gap (the `covered`/`uncovered`
label in §3).

**Decision rule (pre-registered):** build the harvest loop only if
≥ 1/3 of the ungrounded probes on set C are `uncovered`. Below that, the
gap is a retrieval problem and §2 R2 is the whole answer.

**If it triggers, the shape is a harvest loop, not bulk generation:**

- Source: probe targets (`topic` + `question_hint` + `expected_points`)
  from set C and from opt-in mock session logs, deduplicated with the
  ingest's lexical-containment rule. Only topics that recur or that a JD
  default template hits every time; never "generate 200 chunks".
- Pipeline: reuse `grader/ingest_questions.py`'s `generate_rubric` /
  `build_chunk` with a new candidate source `generated:probe`; free dry
  run, `--generate --confirm`, ≈ $0.03 per chunk (rag_exp measured 57 for
  $1.77). Idempotent, like the ingest.
- **Human review is mandatory** — every promoted chunk is read and edited
  before it lands. The circularity risk is real (LLM question, LLM rubric,
  LLM grading) and review is the only human anchor.
- Placement: a separate bank (`rag_gen/`, mock-grounding only — not a
  practice track), so "Real Qs" stays honestly real and the corpus count
  reports tiers, not one inflated number.
- Visibility: `metadata.source = "generated:probe"`; the mock report shows
  a third rubric tier ("reviewed generated rubric") beside "bank rubric"
  and "expected specifics". Generated chunks stay out of the retrieval
  eval labels and out of grader training unless teacher-labeled.
- Measure it like everything else: grounding coverage on set C before vs
  after, and the share of a real session's probes that land on each tier.

**Résumé value:** modest alone; strong as the decomposition line — "X% of
grounding gaps were retrieval misses, Y% were content gaps; fixed each with
the right tool."

## 11. What the set C result means (written after the run)

The plan assumed the mock's grounding gap was *coverage*: probes that score
below BM25's threshold and fall back to the planner's on-the-fly rubric. The
measurement says otherwise. Probe queries are `topic + question_hint` — long,
resume-specific sentences ("You said TimeSeriesSplit prevented leakage. What
leakage would happen with random splitting on transaction data...") — and
raw BM25 score grows with query length, so 77/77 probes clear the bar of 10.
The gap is *precision*: 34 of BM25's 77 attachments were judged unfair
rubrics for their probe (56% precision), and of those, 25 had a fair chunk
somewhere in the banks (retrieval misses) while 9 had none (content gaps —
retraining triggers, reranker cost/latency, ML reproducibility and CI/CD,
label maturity, capacity planning, handoff).

Sliced (15–16 probes per JD, 38–39 per level, so one probe is 6–7 points;
tables in the report): the candidate *level* barely matters — Mid-level
56 / 67 / 69% for BM25 / hybrid / dense, Senior 55 / 55 / 61%. The *job
description* matters a lot — BM25 leads on the MLE posting (88% vs dense
62%), dense leads on the data-science posting (87% vs 40%), and every arm
is poor on the AIE posting (38–50%). The sharpest cut is the probe's
*source*: probes drawn from the resume's own project ground fairly 69–74%
of the time in every arm, probes drawn from the JD's role themes only
26–43%, and 7 of the 9 content gaps are role themes. The banks cover the
example resume's fraud-model vocabulary well (imbalance, temporal splits,
thresholds, deployment); they do not cover what a posting asks *beyond*
the resume (reproducibility, capacity, reranking cost, handoff). That is a
bank question as much as a retrieval one.

**Product decision taken on this evidence (2026-09-04, user):** the mock's
probes now come from the resume only. The JD decides which resume claims
get probed and how deep (`jd_emphasis`), never adds topics the resume
lacks; the beyond-resume path is frozen behind `MOCK_BEYOND_RESUME` until a
bank of beyond-resume interview questions has been gathered to ground it.
By construction that moves grounding to the project-probe row above
(69–74% fair, 2 gaps in 54).

Consequences, none of them shipped today because none was pre-registered:

1. **Grounding is a precision problem, so R2 was the wrong rule.** A rule
   for the next round should hold coverage and trade it for precision: e.g.
   "switch the grounding arm only if hand-labeled precision rises by ≥ 10
   points at ≥ 90% of BM25's coverage". Dense at the calibrated threshold
   measured 65% vs 56% on the same 77 probes — +9 points, and it would have
   needed a rule to ship under. It gets one next time, with fresh probes.
2. **A wrong rubric is worse than none.** Today an unfair attachment makes
   the report grade a probe against key points that do not fit it. The
   cheapest mitigation is not a better retriever but a *precision-side*
   threshold on BM25 (the calibration curve in the report shows attach rate
   vs precision) — worth its own small pre-registered rule.
3. **§9 stays off.** 12% content gaps is real but below the 1/3 line, and
   the gaps cluster in MLOps topics (reproducibility, capacity, retraining)
   that the course banks were never about. If they matter for the mock,
   they are a *bank* decision, not a retrieval one.

The labels behind all of this were made in-session by the assistant and are
editable in `grader/grounding_labels.jsonl`; the author's spot-check may
move the precision numbers by a few points but is unlikely to move the
conclusion, since coverage — the pre-registered quantity — is 100% by
construction.

**Agreement finding (post-hoc, same labels).** When BM25 and dense pick
the *same* chunk, the attachment is fair 28/31 times over all probes and
25/25 on resume-project probes. When they disagree, every arm is a coin
flip — BM25 41%, dense 52%, hybrid 48% on resume-project probes; hybrid
does not rescue a disagreement, it averages a good pick with a bad one.
Score alone separates less well: dense cosine has fair median 0.774 vs
unfair 0.690 (a floor at 0.70 keeps 38/40 fair and admits 5/14 unfair);
BM25 raw score fair median 20.8 vs unfair 16.4. Per-JD routing was
considered and rejected: cells of 8–13 probes, and the JD is a proxy for
probe style, not the cause. These numbers were found *after* looking, on
the assistant's labels — which is why §12.4 turns them into a rule to be
tested on fresh probes rather than shipping them.

## 12. Phase 2 (revised) — grow the banks, then measure grounding once

*Written 2026-09-04 before any of it starts; the author reviews this
section before the build session. Sequencing decision: the grounding
experiment measures precision against the bank as it is, so the bank grows
first and the experiment runs once, on the grown bank, with one labeling

### 12.1 The rule that governs the growth: add, never rewrite

Chunk ids are load-bearing beyond retrieval: `grader/dataset.jsonl` and
the gold labels join on them, bookmarks store them in the browser, the plan
cache and the rag_exp overlap check reference them. A "re-chunk" that
replaces the AIE chunks would silently orphan the grader's gold labels.
Growth is therefore an **expansion**: every existing chunk stays as it is;
new claim-level chunks get new ids and a metadata `source` that says where
they came from (`course:expanded`, `paste:<file>`, or a GitHub repo id).
The public banks are regenerated from the private complete ones by
`tools/strip_chunks.py` exactly as today; lesson text never enters the
public repo.
